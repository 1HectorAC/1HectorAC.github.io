2. Extending User(Identity)

One of the first issues I ran into was a database schema issue involving the user in ASP.NET Identify (Microsoft system for managing users). I need to have the user model have a list of MediaItems in order to setup the one to many relationship between them. The issue is that the default user in Identify is auto created. The solution I found was to create a user model class (stores any other fields you want the user to have) that extends IdentityUser (this is the default user type used in Identity), and then passing that to the dbContext as well as in the program file when setting up the dbContext DI. Below is some of the code to show how it was setup: 


// ApplicationUser.cs
//extending IdentityUser
public class ApplicationUser: IdentityUser
{
    public ICollection<MediaItem> MediaItems {get; set;} = [];
}

// AppDbContext.cs
public class AppDbContext: IdentityDbContext<ApplicationUser, IdentityRole, string>
{...}

// Program.cs
builder.Services.AddDefaultIdentity<ApplicationUser>()
    .AddRoles<IdentityRole>()
    .AddEntityFrameworkStores<AppDbContext>();

3. API Setup

The next thing I had to figure out was calling an API. I have previous experience dealing with APIs, but I haven't really done so in ASP.NET Core and I knew it was going to be more verbose than doing in JavaScript. A quick search lead me to 3 main ways to make an API request. The first is creating an instance of the HttpClient. This is the least recommended way given that it doesn’t have any socket management setup. The second is using a HttpClientFactory and creating instances of the HttpClient with it (you can setup DI). This method does have socket management as well some other stuff. The final way is "Named Client", which uses HttpClientFactory under the hood with some added information, specifically a class that get setup with configurations when setting up DI. I stuck with the best practice option which is Named Client. Here is how I set it up: 


//Program.cs
//DI Setup:
builder.Services.AddHttpClient<GeminiService>("Gemini", client =>
{
    client.BaseAddress = new Uri("https://generativelanguage.googleapis.com/v1beta/");
    client.DefaultRequestHeaders.Add("x-goog-api-key",
    Environment.GetEnvironmentVariable("GEMINI_API_KEY")
    );
});

// GeminiService.cs
public class GeminiService
{
    private readonly HttpClient _http;

    public GeminiService(HttpClient http)
    {
        _http = http;
    }
    public async Task<string> GenerateTextAsync(string prompt)
    {
        var body = new { model="gemini-3.6-flash", input = prompt};
        //var json = JsonSerializer.Serialize(body);

        var response = await _http.PostAsync(
            "interactions",
            JsonContent.Create(body)
        );

// Any Class that needs to call API
//Example use:
// add GeminiService as readonly variable and set with contructor
var result = await _geminiService.GenerateTextAsync(prompt);

4. Pagination/Filter/Search

For this part I decided to go over Pagination/Filters/Searches all together since they are related and it saves me time. The context that we are talking about here is visiting a page with a table of items that can then be filtered in some way (either by the name, some filter, or restriction of page quantity). The core flow/steps involved are as follow:

  • User visits page
  • Action method has parameters with default values(page=1, pageSize=3, searchTerm… other filters)
  • Action method gets list of items and applies filters as needed (which is not much at first, just page restrictions)
  • Action method returns View + ViewModel (list of data, values mention above, some extra calculated data like TotalItems, TotalPages, hasPrevPage, hasNextPage)
  • View is visited by User: can hit filter+submit or next page button
  • Note: Next Page Button is a link element that references the same page but also passes in all values from the ViewModel with page number being incremented
  • Note: filter+submit section is a from to the same page but will also have some of the values from the ViewModel set in input secret elements
  • If "Next" or "Filter+Submit" is hit, will make request to same page but with added parameters
  • Repeat the process, but this time values are passed rather than using default values

5. Active Nav Item

Last part I wanted to mention was how to highlight the current nav Item in the navbar in ASP.NET Core MVC app. The way you do this is that in the _Layout.cshtml page, you first get the Controller and Action name. These can be retrieved with the ViewContext. With the Controller/Action names you can then just add an "if" check in each nav Link to add a styled "active" class. Example shown below. 


// _Layout.cshtml
// section below must be in body element
@{
        var currentController = ViewContext.RouteData.Values["controller"]?.ToString() ?? string.Empty;
        var currentAction = ViewContext.RouteData.Values["action"]?.ToString() ?? string.Empty;
    }
//  Example class value for navbar "a" element
"nav-link @(currentController == "Home" && currentAction == "Index" ? "active" : "")"
